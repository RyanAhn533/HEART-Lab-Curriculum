# 2-8. 왜 새 데이터에서 안 되는가 — 과적합과 일반화

> **Ref: Coursera C1W3 과적합 / Stanford CS229 W4 편향-분산 / Google MLCC "Generalization"**

---

## 왜 배우는가

모델이 훈련 데이터에서 99%를 맞추는데, 새 데이터에서 60%밖에 안 맞는다.
이게 **과적합(Overfitting)** — ML에서 가장 흔하고 중요한 문제.

---

## 1. 과적합 vs 과소적합

### 과소적합 (Underfitting)
- 모델이 **너무 단순**해서 데이터의 패턴을 못 잡음
- 훈련 성능도 낮고, 테스트 성능도 낮음
- 해결: 모델을 복잡하게 (레이어 추가, 특성 추가)

### 과적합 (Overfitting)
- 모델이 **너무 복잡**해서 훈련 데이터의 **노이즈까지 외워버림**
- 훈련 성능은 높은데, 테스트 성능은 낮음
- 해결: 정규화, Dropout, 데이터 추가, 조기종료

### 적절한 적합 (Good Fit)
- 훈련과 테스트 성능이 모두 적절히 높음

```
과소적합        적절한 적합       과적합
 ─────          ─────          ─────
 /              ╱╲             ∿∿∿∿
/           ───╱──╲───      ∿∿∿∿∿∿∿
              ╱    ╲
"너무 단순"    "딱 맞음"     "노이즈까지 외움"
```

---

## 2. 편향-분산 트레이드오프 (Bias-Variance Tradeoff)

| | 높은 편향 (High Bias) | 높은 분산 (High Variance) |
|---|---|---|
| 모델 | 너무 단순 | 너무 복잡 |
| 결과 | 과소적합 | 과적합 |
| 훈련 성능 | 낮음 | 높음 |
| 테스트 성능 | 낮음 | 낮음 |
| 해결 | 모델 복잡하게 | 정규화, 데이터 추가 |

**목표: 편향과 분산 사이의 균형점 (sweet spot)**

---

## 3. train/test 분할 — 왜 나누는가

모델을 만든 데이터로 평가하면 **시험 문제를 미리 알고 시험 보는 것**과 같다.

```
전체 데이터
├── Train (80%) — 모델 학습용
└── Test (20%)  — 모델 평가용 (학습에 절대 사용 안 함)
```

더 엄밀하게:
```
전체 데이터
├── Train (60%) — 모델 학습
├── Validation (20%) — 하이퍼파라미터 튜닝
└── Test (20%) — 최종 평가 (한 번만 사용)
```

---

## 4. 교차검증 (Cross-Validation)

한 번의 split으로는 **우연히 좋거나 나쁜 결과**가 나올 수 있다.
데이터를 K등분해서 K번 반복 → 평균 = 안정적인 평가.

```
Fold 1: [Test] [Train] [Train] [Train] [Train]
Fold 2: [Train] [Test] [Train] [Train] [Train]
Fold 3: [Train] [Train] [Test] [Train] [Train]
Fold 4: [Train] [Train] [Train] [Test] [Train]
Fold 5: [Train] [Train] [Train] [Train] [Test]

→ 5번 평가의 평균 = 최종 성능
```

---

## 5. 정규화 (Regularization) — 직관만

과적합을 방지하는 방법. **"가중치를 너무 크게 만들지 마라"**

| 방법 | 설명 |
|------|------|
| L2 (Ridge) | 가중치 제곱합에 페널티 → 작게 유지 |
| L1 (Lasso) | 가중치 절대값합에 페널티 → 일부를 0으로 |
| Dropout | 뉴런을 랜덤으로 끔 (Chapter 4 이후에서 다룸) |
| EarlyStopping | 성능이 더 안 좋아지면 멈춤 (Chapter 4의 4-8에서 다룸) |

**Ridge의 `alpha`도 하이퍼파라미터다** — 제약의 강도.
0에 가까울수록 정규화 없는 것과 같아지고(과적합 방향), 너무 크면 과소적합 방향. 실습에서 alpha를 스윕하며 확인한다.

---

## 6. 시드와 재현성 (Reproducibility)

계속 나오던 `random_state=42`의 정체:

- 데이터 분할, 셔플, 가중치 초기화에는 **난수**가 들어간다 → 실행할 때마다 결과가 달라질 수 있음
- 시드를 고정하면 **같은 코드 = 같은 결과** → 디버깅과 비교가 가능해진다
- 42는 관습일 뿐, 아무 숫자나 상관없다

**주의**: 시드 하나의 결과는 "그 시드에서의 결과"일 뿐이다.

- 시드를 바꾸면 성능 숫자가 달라질 수 있다 (특히 데이터가 적을 때)
- 그래서 연구/논문에서는 **여러 시드(예: 5개)로 돌려서 평균 ± 표준편차**로 보고하는 게 표준
- 좋은 결과가 나온 시드만 골라 보고하는 "시드 튜닝"은 자기기만이다
